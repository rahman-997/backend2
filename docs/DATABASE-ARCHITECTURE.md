# Database Architecture

## Runtime storage contract

The service exposes one storage-independent `VenueRepository` contract and currently has three implementations:

```text
VenueRepository
├── MemoryVenueRepository
├── PostgresVenueRepository
└── MySqlVenueRepository
```

The controller and service layers do not contain PostgreSQL- or MySQL-specific business logic. Runtime selection is controlled by `STORAGE`.

## PostgreSQL

PostgreSQL remains the default production target and the canonical database for the ORM compatibility tooling.

- migrations: `migrations/`
- connection: `DATABASE_URL`
- runtime: `STORAGE=postgres`
- driver: `pg`
- schema contract command: `npm run db:contract`

PostgreSQL migrations are tracked in `schema_migrations` and are transactional where PostgreSQL permits.

## MySQL

MySQL 8.4 is a first-class runtime database adapter.

- migrations: `schema/mysql/`
- connection: `MYSQL_URL`
- runtime: `STORAGE=mysql`
- driver: `mysql2`
- schema contract command: `npm run db:contract:mysql`

MySQL migrations are tracked in MySQL's own `schema_migrations` table. MySQL DDL may implicitly commit, so migration files are written to be safely repeatable when practical and are marked applied only after successful execution.

The MySQL schema enforces:

- UUID-compatible `CHAR(36)` primary keys generated by the application
- case-insensitive venue-name uniqueness
- positive integer capacity
- email length <= 320
- created/updated timestamps
- capacity and created-at indexes

## Docker topology

Docker Compose runs both SQL adapters at the same time through separate API containers:

```text
api :3000
  -> PostgreSQL 17

api-mysql :3001
  -> MySQL 8.4
```

Both API containers are built from the same production image. The image runs `dist/db/migrate.js`, which selects the correct migration dialect from `STORAGE`, before starting `dist/server.js`.

## ORM schema representations

The ORM tooling currently targets PostgreSQL and is intentionally separate from runtime database selection:

- `prisma/schema.prisma` — Prisma validation/generation
- `drizzle/schema.ts` — Drizzle schema checks
- `src/db/typeorm/Venue.entity.ts` — TypeORM metadata validation
- Zod schemas — HTTP boundary validation; not database migrations

Prisma, Drizzle, and TypeORM are not chained together in production requests. They are development/tooling dependencies used to prove schema compatibility and exercise the PostgreSQL representation.

## Ownership rules

1. A request uses exactly one persistence adapter.
2. `STORAGE` chooses memory, PostgreSQL, or MySQL at process startup.
3. ORM synchronization must never mutate production schema automatically.
4. PostgreSQL and MySQL use dialect-specific migration directories.
5. Both SQL adapters must preserve the same HTTP/domain behavior.
6. CI must validate both database contracts and run the same compiled API E2E scenario against both SQL adapters.

## Shared domain requirements

Both SQL databases preserve the following contract:

- server-generated UUID-compatible ID
- case-insensitive unique venue name
- required address
- positive integer capacity
- contact email bounded to 320 characters
- timestamps
- paginated list queries
- name/address search
- inclusive min/max capacity filtering
- safe allowlisted sorting
- duplicate writes surfaced as HTTP `409`
- health/readiness checks
- graceful connection-pool shutdown
